## 2. 素材

- 44 支 Wikimedia Commons 影片，共 25.3 分鐘，授權只收 CC0、公有領域、CC BY、CC BY-SA。清單在 `datasets/manifests/commons_manifest.json`，包含來源網址、作者、授權和兩份 SHA-256（原檔與轉檔）。
- 統一轉成 H.264 MP4（最寬 1280 px、無聲）。逐支比對轉檔前後長度：43 支一致；028（Nespresso）的原始檔本身有壞掉的封包，轉出來是 41.0 秒（原本 44.7 秒）。標註和評分都用同一個轉檔，所以保留，紀錄在 `transcode_check.json`。
- 依上傳者分組切成 dev 18 支、test 26 支，同一位上傳者不會同時出現在兩邊。
- 片單裡刻意放了反例：茶、啤酒、氣泡酒、空杯、街景、酒吧、公園。

## 3. 標註

- 兩位標註者各自看每秒一格的接觸表，彼此看不到對方的結果，也看不到系統輸出。
- 一致性：clip × 需求層級 472/484（97.5%），逐樣本 Cohen's κ = 0.914。
- 143 個有分歧的影格交給第三位裁決者，盲審（不知道誰標了什麼）。裁決者寫下 8 條規則，處理規範沒講清楚的地方，例如「居家沖煮算不算咖啡師」「膠囊機算不算義式萃取」。
- 一致性複審：同一套規則再套到兩人都同意的 238 個影格上，移除 78 個（大多是居家或教學影片裡的 SH-11）。這一步在任何模型輸出之前就決定，並寫進協議。
- 兩位標註者的原始標註都原樣保留在 `eval/labels/raw/`。主要答案是 `gold.json`，寬鬆版本 `gold_lenient.json` 一起評分。

## 4. 校準（只用 dev）

- 兩種裁切方式（中央裁切、補邊成正方形）都在 dev 組試過，選逐幀 F1 較高的中央裁切，門檻 τ = 0.225（F1 0.240），19:22 凍結。

## 5. Test 只評一次（19:22）

| 方法 | Recall@5 | Precision@5 | 缺口召回 | 誤報補拍 |
|---|---|---|---|---|
| 片名關鍵字 | 45% | 36% | 89% | 44% |
| 單幀語意搜尋 | 73% | 40% | 0% | 0% |
| SceneGap | 64% | 33% | 0% | 0% |

- 對 11 條需求，SceneGap 有 7 條在前 5 名裡找到正確片段。
- 自動判斷「素材裡沒有」這件事沒有做到：門檻是用逐幀 F1 選的，太寬鬆，幾乎每條需求都能找到某個候選，所以沒有一條被判成「沒找到」。
- 寬鬆版答案的結果幾乎一樣（關鍵字 Recall@5 從 45% 變 55%，其他不變）。
- 要人看的候選片段約 317 秒，整批 test 素材 839 秒。

## 6. 評分之後的分析（只用 dev，不改 test 結果）

- 在 dev 組模擬 20 個小專案，掃不同門檻：門檻提高到 0.29 時缺口召回 46%，但誤報補拍升到 31%；換成「減掉通用提示相似度」的相對分數，誤報補拍 11% 時缺口召回 33%。
- 結論：單幀 CLIP 加一個共用門檻，不夠用來判斷「缺鏡頭」。第二階段改成每條需求各自校準、以專案層級的缺口判斷當校準目標，並在新素材上重新預先登錄、只評一次。

## 7. 效能（桌機參考後端）

| 後端 | 每分鐘影片分析時間 | 模型載入 | 搜尋 10,000 段 p50／p95 |
|---|---|---|---|
| CPU | 3.1 秒 | 6.5 秒 | 11.8／14.3 ms |
| RTX 4080 GPU | 2.3 秒 | 1.9 秒 | 7.6／13.4 ms |

- 每秒取一格時，主要成本是解碼，不是模型。
- 播放干擾（代理測試）：一邊用 SceneGap 分析、一邊即時解碼 1080p30 影片，1,800 格中 0 格延遲；每格處理時間 p95 從 5.7 ms 變成 7.5 ms（CPU 分析時）、6.2 ms（GPU 分析時），預算是 33 ms。播放期間背景確實分析完 22 支（CPU）和 52 支（GPU）片。
- UGen300 還沒接上，G1 量測腳本已準備好；用 CPU 對 GPU 自我檢查時 cosine 1.0、ρ 0.99999。

## 8. 工程驗收
